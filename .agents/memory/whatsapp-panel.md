name: WhatsApp panel decisions

## QR codes must be rendered locally
Render the Baileys QR/pairing string with the local `qrcode` package (e.g. `QRCode.toDataURL`), never via an external image service like `api.qrserver.com`.
**Why:** the QR `state.qr` value is the live WhatsApp linking payload. Sending it to a third party exposes a session-pairing path. A prior version used `api.qrserver.com` — that is a credential-exfiltration risk.
**How to apply:** any connect/QR UI must keep `state.qr` on-origin.

## Admin panel is monitoring-only
The admin dashboard must not be able to send WhatsApp messages — UI form AND the backend route must both be absent. The `POST /admin-panel/send` route was intentionally removed.
**Why:** product requirement — admin oversees all incoming/outgoing traffic but never originates messages. Hiding only the UI is not enough; an authenticated admin token could still call the route.
**How to apply:** if asked to add admin messaging, confirm intent first — it contradicts the monitoring-only design.

## Connection backend already works
The working Baileys connection lives in `multiWhatsapp.ts` (connectQR / connectPhone pairing). Reported "connection not working" complaints have been about QR UX (manual tap, no auto-generate), not the backend. The pairing-code flow (type number → 5s → requestPairingCode) mirrors the known-good `services/whatsapp.ts`. Pairing-code is the default connect mode (user finds it easiest); QR is an opt-in tab that auto-generates on open.

## "Complete WhatsApp Web" needs history sync, not just live capture
`messages.upsert` (type `notify`) only captures messages that arrive AFTER the device links — so the inbox starts empty. To make existing chats/messages appear like WhatsApp Web, you MUST also handle the Baileys `messaging-history.set` event and persist its chats+messages. Mark these as `history` so old inbound messages do NOT inflate unread counters.
**Why:** users link an account and expect their real conversations to show up immediately; without history sync the panel looks broken/empty.

## Every message showing "Media" = unwrap Baileys envelopes
If chats/messages all render as "📎 Media" (no real text), the parser is reading the top-level proto without unwrapping. Baileys wraps real content in envelopes: outgoing-from-phone → `deviceSentMessage.message`, disappearing chats → `ephemeralMessage.message`, view-once → `viewOnceMessage(/V2/V2Extension).message`, plus `documentWithCaptionMessage.message` and `editedMessage.message`. Unwrap (loop, content can be doubly-wrapped) BEFORE extracting conversation/extendedTextMessage/captions.
**Why:** the user's own outgoing messages and any disappearing-message chat were all falling through to the "Media" fallback.

## Correcting already-persisted message rows on re-sync
In-memory dedup (`upsertMsg` only persists when a message is newly `added`) means a re-link/history replay will NOT re-write rows already in the DB — so a parser fix alone won't repair old bad rows. To backfill: when an existing in-memory message is re-seen with better/different non-empty text (and isn't deleted), update it in memory AND call notifyPersist; pair that with `onConflictDoUpdate` on `wa_messages` (keyed on waMessageId) whose text uses `CASE WHEN deleted THEN keep ELSE new` so delete markers survive.
**How to apply:** any "old data is wrong after a parser/format fix" situation needs both a re-emit path through dedup AND a conflict-update at the DB layer.

## Admin chat monitor = master-detail, not split, and must poll the open chat
Admin "All Chats" should be tap-to-open like normal WhatsApp: show the full-width list when no chat is active, and a full conversation view (with a back button that clears activeChat) when one is tapped — not a cramped side-by-side split that strands "Select a chat" on mobile. The open conversation must have its OWN polling effect keyed on the active jid; the main dashboard `loadAll` poll does not refetch the open chat's messages.

## Persist-listener flag propagation gotcha
The persist pipeline is a two-hop listener chain: `UserSession.notifyPersist` → per-session listener → `MultiWhatsAppService.getSession()` bridge listener → global listeners in `chatPersistence`. When you add an arg (e.g. the `history` flag) to `PersistListener`, you must forward it through BOTH hops. The bridge in `getSession()` is easy to miss and silently drops the arg (it becomes `undefined`), defeating the flag.
**How to apply:** any new field on a listener signature must be threaded through every relay closure, not just the emit site.

## Real media rendering — download + serve, don't store inline in chat payload
Media (photo/voice/video/doc) shows as a placeholder unless you actually `downloadMediaMessage` (Baileys) in BOTH the live `messages.upsert` and the `messaging-history.set` handlers. Store the bytes as base64 in `wa_messages.media` (+ `mediaMime`/`mediaKind`/`fileName`). Cap downloads (8MB) and pass `reuploadRequest: sock.updateMediaMessage` so expired media can be re-fetched. The chat-list/messages query must EXCLUDE the base64 blob (return only `hasMedia` + meta) and serve bytes lazily from a dedicated `/media/:msgId` route, or every poll drags megabytes.
**Why:** inlining base64 in the messages list response makes polling huge and slow; placeholder-only happens when the download step is skipped.

## Media route auth via `?t=` token is required for <img>/<audio>/<video> src
Browser media tags can't send an Authorization header, so the media serve routes accept the bearer token as `?t=` query param (mirrors the existing events/SSE route pattern) and set it as the auth header server-side. Known tradeoff: token leaks via logs/history; acceptable here because it's a single-panel-user (PANEL_USER_ID=1) monitoring app. The USER route now scopes `getMediaById(id, accountPhone)` by the currently-linked number (admin stays unscoped), closing the cross-account media IDOR — scoping the messages LIST alone left a hole where an old number's media was still fetchable by guessing a message id. A future multi-user scope would still want short-lived signed media URLs.

## Backup restore must map EVERY persisted column
Backup export uses `select().from(waMessagesTable)` (all columns), but restore re-maps fields explicitly — so any NEW column (e.g. media/mediaMime/mediaKind/fileName) is silently dropped on restore unless added to the restore mapping too.
**How to apply:** whenever you add a `wa_messages` column, update the restore `.map()` in `panel.ts` in lockstep, or restored media/data vanishes.

## Media download must be non-blocking, and its backfill must not re-count unread
In the live `messages.upsert` handler, do NOT `await downloadMediaBase64` before `upsertMsg` — that delays (and if it throws, drops) the message, killing the real-time feel. Instead upsert the placeholder immediately, then download in the background and re-`upsertMsg({...chatMsg, media})` to backfill. CRITICAL: pass `history=true` on that backfill call, otherwise the second persist increments `wa_chats.unread` a SECOND time (persistMessage bumps unread whenever `!history && !fromMe`, and it can't tell a correction from a new message) → inbox badges inflate by 2 for every inbound media message.
**Why:** the user reported messages felt slow/not-updating after media was added; the blocking await + double-count were the cause.

## "Failed to fetch stream" on bulk media = burst concurrency, not CDN/reupload
When many media messages land at once (e.g. a 50-photo dump), downloading them all in parallel saturates the single Baileys websocket and the CDN fetches start failing with "Failed to fetch stream" — even though `reuploadRequest` is already wired and the VPS↔CDN path is healthy (a manual fetch returns fast, HTTP 200 in ~0.03s). Fix is a small GLOBAL semaphore (cap ~3) wrapping the download/retry, NOT more retries or a CDN/network change.
**Why:** root-caused ~125 such failures in one day to concurrency after confirming CDN reachability and that reupload was present.
**How to apply:** for any "media intermittently fails under load" report, throttle concurrent downloads before suspecting the network or Baileys media expiry.

## Never log the panel user out on transient errors
`useRequirePanelAuth` (and polling catch handlers) must only clear the token + redirect to /login on a genuine **401/403**. The panel token is a deterministic HMAC with NO expiry, so it's valid until the password changes. A network blip or API restart makes `/panel/me` reject — clearing the token there logs the user out spuriously. `panelApi.handle()` attaches `err.status`; gate logout on `err.status === 401`. On other errors keep the session (optimistic `setUser`).
**Why:** user explicitly wants the session to persist "even a year" until they delete authorization.

## In-app back button must not depend solely on pushed history
Chat-open pushes `history.pushState({scChat}, "")`; the ◀ button checks `window.history.state?.scChat` and uses `history.back()` if present, else closes directly (`setActiveJid(null)`). Without the fallback, if the entry wasn't pushed, `history.back()` navigates the real history (e.g. to /connect) instead of returning to the chat list — exactly the bug the user hit.

## Default theme = authentic WhatsApp WHITE-GREEN (`:root` light palette)
User explicitly wanted real WhatsApp white+green colors/styles, NOT a dark theme. Achieved by removing `class="dark"` from `index.html` so the existing `:root` light palette (white bg, green `#00a884` / `--wa-header: 168 100% 33%`) applies. `:root` was already authentic WhatsApp — the only change needed was dropping the forced `.dark`. Keep `theme-color` meta green. Do NOT reintroduce a dark default.

## VIP theme is an additive opt-in skin, never a replacement
The default look (now WhatsApp white-green `:root`) must stay untouched. VIP is added by also putting a `vip` class on `<html>`; `index.css` `.vip` block must come AFTER `.dark`/`:root` so its overlapping CSS vars win the cascade. `.vip` defines a FULL self-contained palette so it works regardless of whether `.dark` is present. State lives in localStorage `wa_theme_vip`, applied by `applyTheme()` in `main.tsx` before render (avoids flash). Toggles exist in BOTH user Settings and admin header. `clearCache()` in settings must EXEMPT `wa_theme_vip` (it otherwise matches the `wa_` purge prefix and silently resets the theme).
**Why:** user said "Sirf VIP theme add karo, baaki rehne do" — add VIP only, keep the rest.

## Connect-first flow (WhatsApp-Web style) — guard against redirect ping-pong and the disconnect trap
chats.tsx redirects to `/connect` when WA isn't connected, but ONLY after the first real status fetch (a `connChecked` flag, avoids a flash) and NEVER while a conversation is open (`activeJid`). connect.tsx auto-navigates to `/` ONLY on a fresh link: track the FIRST observed status in a `firstConnected` ref (null→set on first fetch); auto-redirect only when `firstConnected.current === false && connected`. If you redirect whenever `connected`, a user who opens Connect on purpose to disconnect gets yanked away and can never disconnect. Keep a manual "Open Chats" button as the flaky-network fallback.

## Spurious logout root cause = unordered single-row token lookup
Panel token = HMAC(SESSION_SECRET, `panel:userId:passwordHash`); secret has a stable constant fallback so it's NOT the cause. The real bug: `getUserFromToken` fetched the panel user with `db.select().limit(1)` UNORDERED. Once a 2nd row exists (a pending signup), that picks an arbitrary/wrong user, the HMAC compare fails → 401 → client logs out. Fix: iterate ALL panel users and match each. **Rule:** any token whose verification depends on a DB row must look up the RIGHT row (decode an id or iterate), never an unordered `limit(1)`.

## Chat opens at the top, not the last message = UNBOUNDED scroll container
`getChatMessagesDb` is `asc(ts)` so order is correct; JS scroll-to-bottom alone is NOT enough. Root cause was the Conversation root div using `min-h-screen` — the parent grows past the viewport so the PAGE BODY scrolls, the inner `flex-1 overflow-y-auto` pane never gets a bounded height, and `scrollRef.scrollTop = scrollHeight` is a no-op. Fix: pin the conversation root to `h-[100dvh]` (fixed viewport height) so the inner div is the real scroller. **Rule:** a `flex-1 overflow-y-auto` child only scrolls if an ancestor has a FIXED height (`h-screen`/`h-[100dvh]`), never `min-h-screen`. Pair with: jump to bottom on first open (`didInitialScroll` ref reset on `jid`), near-bottom gate on poll refresh, `requestAnimationFrame` before setting scrollTop.

## Phone-sent (WhatsApp→WhatsApp) messages need Baileys `append`, not just `notify`
`messages.upsert` fires with `m.type`: `notify` = brand-new live message arriving here; `append` = messages added from ELSEWHERE, **including the messages you send from your own phone**. A handler that does `if (m.type !== "notify") return;` silently drops all phone-sent outgoing → they never appear in the panel. Fix: accept both; `isLive = m.type === "notify"`; call `upsertMsg(jid, m, display, !isLive)` so `append` is treated like history (persisted + updates lastMsg/lastMsgTs, but no unread inflation); gate incoming-routing (`incomingKeys` + `notifyMsg`) on `!fromMe && isLive`. Dedup is safe (id-based merge + DB `onConflictDoUpdate`). Edge case (low-prob): a genuinely-new INCOMING as `append` won't bump unread/route.

## Live message sync ALSO depends on a PERSISTENT deployment (Baileys websocket)
Even with the `append` fix, in the PUBLISHED app Baileys holds a long-lived websocket + local `.user-sessions` auth files, which autoscale tears down/spins between instances → fresh messages stop. Must deploy as a Reserved VM (single always-on instance). Polling in dev (`/panel/chats` 4s, open conversation 3s) works fine locally.

## Pairing code generates but doesn't link = environmental, not code
Baileys is already latest (`7.0.0-rc13`) and the connectPhone pattern is sound. If a pairing code shows but the phone never links, it's WhatsApp-side (account linked on too many devices, or a stale/"Bad MAC" session), not a bug to chase in code. Guard the request with `if (sock.authState.creds.registered) return;` before `requestPairingCode`. Advise the user to try QR once as a diagnostic and to ensure the number isn't over-linked.

## Custom-branded pairing code IS supported by Baileys (not a hack)
`requestPairingCode(phoneNumber, customPairingCode?)` accepts a second arg: a custom code that REPLACES the random one (so the OTP can spell a brand, e.g. `HASANALI`). Baileys only validates `length === 8` (no charset check); WhatsApp accepts A-Z/0-9. This is how "Axiom"-style bots show their channel name in the official pairing code. Stored editable in `app_settings.pairing_brand_code` (default `HASANALI`, NOT NULL), normalized to 8 `[A-Z0-9]` chars; threaded route→`multiWA.connectPhone(userId,phone,brand)`→`UserSession.connectPhone`→`requestPairingCode(phone, brandCode)`; falls back to random only when brand isn't exactly 8 chars. `PUT /panel/settings` 400s on a present-but-not-8 value (no silent no-op).
**Why:** user saw another bot do it and wanted the same; it's an official Baileys feature, not an exploit.
Also editable from ADMIN side via `GET/PUT /admin-panel/pairing-code` (requireAdmin; same 8-char [A-Z0-9] normalization+validation as the user route). Both routes write the same singleton `app_settings` row (id=1) — keep validation in sync if one changes. This does NOT break "admin is monitoring-only": that rule is specifically about *sending WhatsApp messages*; settings edits are allowed.

## Anti-delete: keep the ORIGINAL content, only flag the revoke
A "delete for everyone" must NOT overwrite the stored text/media with a placeholder — the whole point of the monitoring panel is to recover what was deleted. A revoke arrives as a Baileys `protocolMessage` with `type === 0` (REVOKE); its `key.id` points at the original message. On revoke: set `deleted=true` + `deletedAt` only, never touch text/media. The revoke envelope itself must be SKIPPED (never persisted) or it stores as a junk "Media" row. Detection must UNWRAP first (`unwrapMessage`) because the revoke can be wrapped in deviceSent/ephemeral. The `wa_messages` `onConflictDoUpdate` text uses `CASE WHEN deleted OR isDeleted THEN keep ELSE new` so a delete marker is never clobbered by a later re-sync.
**Why:** user's headline feature — see deleted messages' real content.

## Anti-delete timing: revoke can arrive before the original is persisted
`markDeleted(id)` is a bare `UPDATE ... WHERE wa_message_id=id` — a no-op if the row isn't stored yet (out-of-order delivery / history sync). Fix: keep an in-memory `pendingDeletes` Set in chatPersistence; `markDeleted` adds the id to it AND runs the UPDATE; `persistMessage` computes `isDeleted = msg.deleted || pendingDeletes.has(msg.id)` so a later-arriving original is written as already-deleted. **Rule:** any "flag by id" that can race its target insert needs a pending-tombstone, not just an UPDATE.

## View-once / once-more media: download the UNWRAPPED message
View-once pics download as nothing unless you pass the unwrapped payload to `downloadMediaBase64`: use `{ key: msg.key, message: parsed.raw }` (parseWAMessage already returns the unwrapped `raw`) in BOTH the live `messages.upsert` and history-sync download calls. Passing the raw envelope makes Baileys fail to locate the media node. Persisted base64 in `wa_messages.media` makes it permanent (survives the WhatsApp "view once" consumption).

## View-once arriving EMPTY on a covert companion is UNRECOVERABLE — show an honest placeholder
Distinct from the entry above (which handles view-once that arrives WITH content). On this covert linked device (`markOnlineOnConnect:false`, never `readMessages`/presence) incoming view-once instead arrives EMPTY: `messages.upsert` fires with `msg.message === null` and `key.isViewOnce === true` (Baileys decode-wa-message tags it from the `unavailable type=view_once` stub; messages-recv excludes `view_once_unavailable_fanout` from auto-resend). Manually calling `sock.requestPlaceholderResend(key, msgData)` DOES fire (returns a requestId) but the phone NEVER returns the bytes — verified LIVE: 3 view-once → 3 resend requests → 0 responses within timeout. This is WhatsApp by design (same reason official WhatsApp Web says "open on your phone"); a companion/linked device cannot decrypt view-once.
**Decision:** do NOT call requestPlaceholderResend for it (it's pure protocol noise that never works = slightly less covert). For `!msg.message && key.isViewOnce` on a real chat jid, upsert an honest PERMANENT placeholder ("🔒 View-once — can only be opened on the phone"), dedupe by key.id, then `continue`.
**Why:** the headline expectation was to reveal view-once content; it is fundamentally impossible on a companion, so the honest signal (that one arrived, with time + sender) is the correct deliverable — don't promise recovery or leave an "opening…" bubble that never resolves.
**IRREFUTABLE RAW PROOF (the test to run if ever doubted again):** add a temporary deep dump in `messages.upsert` — for any `key.isViewOnce` message, log `JSON.stringify(msg.message)` AND `normalizeMessageContent(msg.message)`. Result on this account, connection provably open, multiple sends: `[wa-vo-raw] null` every time, and the summary shows `rawTopKey:null, rawHasVOWrapper:false, normTopKey:null, hasImage:false, hasMediaKey:false, hasUrl:false, hasDirectPath:false`. i.e. `msg.message` is literally `null` — there is NOTHING to unwrap. This directly kills the common "use normalizeMessageContent() / detect the viewOnceMessageV2 wrapper" suggestion: normalize can only unwrap content that exists; here the payload is absent at the wire level. No imageMessage, no mediaKey, no directPath ⇒ `downloadMediaMessage` has nothing to fetch. Per the standard "don't call it impossible unless EVERY test is a stub" bar — every test WAS a stub.
**FULL-LIFECYCLE TRACE (the strongest proof, run when an AI/user insists on tracing "where the payload disappears"):** instrument ALL of `messages.upsert` (later-revisit), `messages.update`, `messaging-history.set` to log any event referencing a tracked view-once id, AND fire a MANUAL `sock.requestPlaceholderResend(msg.key)` (bypassing Baileys' auto-skip) for each stub. LIVE RESULT on this account: 8 view-once → 8 manual resends each returning a VALID reqId (the PDO request was accepted by the phone) → **0** follow-up events ever carried content (no LATER-UPSERT, no UPDATE, no HISTORY with `hasMsg:true`), connection open throughout. So the phone RECEIVES our resend ask and deliberately returns nothing — confirming companion-side withholding, not a missed event. SOURCE CONFIRMS IT: `baileys@7.0.0-rc13/lib/Socket/messages-recv.js` ~L1306-1312 explicitly lists `view_once_unavailable_fanout` among the unavailable types it SKIPS placeholder-resend for (matching WA-Web filters). External: GitHub issue WhiskeySockets/Baileys#2105 (known/by-design), and WhatsApp gates view-once to mobile (screenshot control) — linked-device view-once is a *future* WA feature, not available now. After proving it, REMOVE the manual resend (it's covert noise that never works) and keep only the honest placeholder.
**DEAD-END THEORIES — do not re-chase (both disproven LIVE with `[wa-upsert]` proto logging):** (1) "connection instability causes the empty arrival" — FALSE: with the socket provably `open` and never dropping for minutes, every view-once still arrived `hasMsg:false/viewOnce:true` while NORMAL images in the SAME window arrived `hasMsg:true/imageMessage`. The empty stub is per-message-type, not a connection gap. (2) "`getMessage: ()=>({conversation:''})` vs `()=>undefined` is the regression" — FALSE: tested BOTH values live, view-once arrived empty either way (normal media fine either way). `getMessage` only feeds OUR outgoing resend path; it has zero effect on whether an incoming view-once carries content. (3) "it worked yesterday so a recent code change broke it" — the diff yesterday→today touched only `getMessage` + additive presence code; neither affects incoming view-once. The empty stub is decided by WhatsApp's servers BEFORE Baileys emits the event, so NO config/handler change on our side can fill it. If a user insists view-once worked before, it was WhatsApp's own rollout/flagging, not our regression — verify with the proto log (`hasMsg`), then stop; don't deploy config experiments (each restart destabilizes the live session for nothing).

## Per-account isolation: composite (account_phone, jid) key — IMPLEMENTED
`wa_accounts` (phone PK, first/last_connected_at, connect_count) is upserted via `recordAccount` whenever a session reaches `connected` with a phoneNumber (wired through `multiWA.addGlobalListener` in startPersistence). Each `wa_chats` row is tagged `account_phone` from the currently-linked number at persist time. Admin "Connected Numbers" view filters chats by `accountPhone`.
**Now keyed per-number:** `wa_chats` PK = composite `(account_phone, jid)` and `wa_messages` unique = `(account_phone, wa_message_id)`. The SAME contact jid can exist independently under each connected number, so an old number's chats can NEVER migrate into another number's inbox. The user-side hydrate/persist/clear paths are all scoped to the live `accountPhone` (admin stays unscoped — sees all). This SUPERSEDES the earlier "last-writer-wins / deliberately not done" note: the composite-key refactor was completed and deployed.
**Why the old design was wrong:** jid-only key meant one global chat row per contact, so two SIMs talking to the same contact collapsed into one chat owned by whoever wrote last → cross-account leak. The fix is a genuine schema change, not a display filter.

## wa_* tables empty is usually a USER action, not a deploy/migration bug
`wa_chats`/`wa_messages`/`wa_accounts`/`wa_call_logs` get fully cleared by the admin **"delete entire record"** action (logs `Admin deleted entire record for <number>`) and by **"WhatsApp session cleared" / "auto-fix (fresh start)"** events. `wa_accounts=0` just means no number is currently linked; chats/messages repopulate live once a number links and traffic arrives.
**How to apply:** if prod shows empty WhatsApp tables, check `app_logs` for delete/session-clear events with timestamps BEFORE concluding a migration wiped data. The isolation migration itself only ALTERs constraints + backfills (`INSERT ... ON CONFLICT DO NOTHING`) — it has no DELETE/TRUNCATE/DROP TABLE.

## Show EVERYTHING: groups (@g.us) + status (status@broadcast), not just individuals
`parseWAMessage` historically dropped anything not ending in `@s.whatsapp.net` (groups + status filtered out). To show all chat types, accept `@s.whatsapp.net` OR `@g.us` OR `status@broadcast` in parseWAMessage AND relax the `messages.update` status-tick filter (was also `@s.whatsapp.net`-only) to any non-empty jid. The `messaging-history.set` unread/name capture must also stop being individual-only.
**Why:** user wanted the panel to mirror real WhatsApp — groups, status/stories, and chat-locked numbers all visible.

## Readable chat titles need a name pipeline (groups have NO name on the message)
Individual chats: `msg.pushName` (only on incoming, `!fromMe`). Status: literal "Status". Groups: the subject is NOT on the message — fetch async via `sock.groupMetadata(jid).subject`, cache the jids already fetched (a Set) so you don't refetch, and re-emit a persist so the new name lands in the DB. History sync also carries chat titles in `h.chats[].name/subject` — prefer those. Thread the name through the SAME two-hop persist chain as the `history` flag (notifyPersist → per-session listener → getSession bridge → global listener → persistMessage), then upsert `wa_chats.name` with `COALESCE(new, existing)` so a known name is never wiped by a later nameless message.
**Why:** without this, groups show the raw `…@g.us` id and status shows a number.

## Instant updates = SSE stream, polling demoted to a slow safety net
User's most-emphasized ask was INSTANT background updates. The panel uses a Server-Sent-Events endpoint that registers the same persist/delete/state listeners the DB persister uses, and the frontend drives refreshes off one EventSource (debounced) with the open conversation reloading on a tick counter; polling stays only as a slow fallback. Two rules that bite: (1) EventSource can't set an Authorization header, so the token rides as a `?t=` query param (same tradeoff as the media route); (2) EVERY listener you register on the SSE connection plus the heartbeat interval MUST be torn down on `req.on("close")`, or each reconnect leaks a listener.
**Why:** without SSE the inbox only updated on a multi-second poll, which the user explicitly rejected.
**Caveat:** like live capture, this only works on a persistent deployment (Reserved VM) — autoscale tears down the Baileys socket between instances.

## OTP/pairing-brand editor is ADMIN-ONLY now
The pairing-brand code card was REMOVED from user `settings.tsx` (and its 8-char validation + the field stripped from the PUT payload via destructure). The admin route (`GET/PUT /admin-panel/pairing-code`) stays — that's the only place to edit it. Consistent with monitoring-only = sending only; settings edits allowed on admin.

## Theme system generalized from boolean VIP → named themes (back-compat preserved)
The theme store moved from a boolean VIP flag to a named-theme id, but the old `isVip`/`setVip` API is KEPT as thin wrappers because the admin dashboard header VIP toggle still calls them — and the new getter migrates the legacy boolean key while the setter keeps it in sync, so neither side breaks. Each non-default theme must be a FULL self-contained palette block in `index.css` placed after `.vip` (it has to redefine the whole var set incl the `--wa-*` chat surfaces, not just `--primary`, or surfaces fall back to the default and look broken). Gotcha that silently resets the theme: the settings "clear cache" purge matches the `wa_`-prefixed localStorage keys, so it MUST exempt every theme key.
**Why:** user kept asking for more VIP skins; generalizing beat adding more booleans, but the admin toggle and the cache-clear purge are the two things that quietly break.

## Panel always renders times in Asia/Karachi (never the viewer's tz)
`fmtTime`/`fmtClock` in `panelApi.ts` force `timeZone: "Asia/Karachi"`. The stored `ts` is correct epoch-ms; the bug was `toLocaleTimeString()` rendering in the VIEWER's browser tz — a test/headless browser defaults to UTC, so every time looked ~5h wrong vs the user's WhatsApp clock.
**Why:** user is in Pakistan and compares panel times directly against WhatsApp; "wrong time" complaints are a display-tz issue, NOT a server clock issue.
**How to apply:** the VPS clock is NTP-synced UTC and correct — never chase clock skew for time complaints. Report times to the user in PKT (UTC+5). The "Yesterday" boundary uses a Karachi `dayKey` (`toLocaleDateString("en-CA",{timeZone})`); subtracting 24h is safe because Pakistan has no DST.

## Outgoing tick colors follow the Baileys status enum exactly
Status: 1=PENDING, 2=SERVER_ACK(sent), 3=DELIVERY_ACK(delivered), 4=READ, 5=PLAYED. UI must render: `>=4` blue double-tick (read), `===3` grey double-tick (delivered), else single grey tick. A prior version used `>=3 → blue`, which painted DELIVERED as read so ticks went blue "immediately".
**Why:** recurring confusion — delivered is NOT read; only 4+ is blue.

## User-web is scoped to the CURRENTLY connected number; admin stays unfiltered
The user-facing routes (`/panel/chats`, `/panel/chats/:jid/messages`, `/panel/calls`, `/panel/status`) filter by `currentAccountPhone()` = `multiWA.getSessionInfo(PANEL_USER_ID)?.phoneNumber`, which equals the `wa_*.account_phone` value (format `"+<digits>"`, e.g. `+92XXXXXXXXXX`). When it's null (not connected) the routes return `[]` rather than leaking another number's history. Admin routes are deliberately UNFILTERED (admin sees every number's full history). `getChatMessagesDb`/`getCallLogs`/`getStatusGroups` took an optional `accountPhone` param; `getAllChats` already had one.
**Why:** user wants the user-web to look "fresh per session" — only the number linked right now — while the admin panel retains all history. No DB wipe is needed; filtering achieves the clean view non-destructively.
**Stamping directions (critical, opposite on purpose):** MESSAGE rows are FIRST-writer (`accountPhone = COALESCE(existing, current)`, so a message keeps whichever number first captured it); CHAT rows are LAST-writer (`COALESCE(current, existing)`, so a chat migrates to whichever number most recently sent/received). The chat re-tag is what makes a re-paired number's NEW incoming appear in the account-scoped chats LIST.
**Isolation flip (current — supersedes the earlier "show the full conversation" choice):** `/panel/chats/:jid/messages` IS account-scoped again (passes `currentAccountPhone()` to `getChatMessagesDb`) and `/panel/media/:msgId` is scoped too. New incoming on the LIVE number still shows (its rows are stamped to the live number); only the OLD number's historical messages/media are hidden from user-web and remain ADMIN-only.
**Why:** headline bug — after logging out an old number and linking a NEW one, the old number's data must NOT appear on user-web (admin-only). This deliberately overrides the prior decision to show an opened chat's entire cross-account history; the "incoming not showing" fix it replaced rests on the chat LAST-writer re-tag, which is untouched, so live-number incoming is unaffected.

## TS project references serve stale types after a schema change
`artifacts/api-server` consumes `@workspace/db` via TS project references (reads its built `.d.ts`). After editing `lib/db` schema, `drizzle-kit push` updates the DB but NOT the declarations — api-server typecheck then errors that new columns "do not exist". Run `npx tsc -b lib/db` to rebuild declarations before typechecking the api.

## Single WhatsApp engine — legacy `whatsappService` fully removed
There is exactly ONE WhatsApp engine: `multiWhatsapp.ts` (singleton `multiWA`, auth dir `.user-sessions/user-<id>`). The legacy `services/whatsapp.ts` (`whatsappService`, auth dir `.whatsapp-session`) and its routes (`routes/whatsapp.ts` QR/pairing, `routes/chat.ts` support-widget) were DELETED — a dead parallel engine (no creds on the VPS, never connected) plus a duplicate incoming-routing path. The old customer-support chat widget is gone from the frontend (it calls only `/panel/*` and `/admin*`). Admin reply routes go through `multiWA` only: session-reply uses `sendFromAnyConnected` (best-effort), wa-inbox send uses `sendToJid` and returns 503 if disconnected (no silent legacy fallback). Live persistence is wired solely by `startPersistence()` (registers multiWA persist/status/delete/call listeners + hydrate); the old `app.ts` bot-widget bridge (`routeIncomingWAToBot` + `multiWA.addMsgListener`/`addStatusListener`) was removed too.
**Why:** user repeatedly asked to remove "double"/duplicate code; the legacy engine caused confusion and a duplicate routing path.
**How to apply:** all connect/send/monitor goes through `multiWA`. Do NOT re-introduce a second engine. The `addMsgListener`/`notifyMsg` plumbing in multiWhatsapp.ts is now unused infra (no registrations) — harmless, leave or clean later.

## Monitoring panel must NEVER send read receipts ("seen"/blue ticks)
There is NO `sock.readMessages()` call anywhere. `markIncomingRead` (+ its `incomingKeys` map and manager wrapper) was DELETED. The ONLY read-state op is `markRead()`, which just zeroes the LOCAL `wa_chats.unread` badge — no WhatsApp receipt. Opening a chat in user-web or admin emits no blue "seen" tick to the contact. (Supersedes the older note about `incomingKeys`-gated incoming routing — that map no longer exists; routing is gated on `!fromMe && isLive` via `notifyMsg` alone.)
**Why:** sending blue ticks would tip off the monitored contact and defeat covert monitoring; it was a real leak via the old widget read path.
**How to apply:** never add `readMessages`/`sendReceipt`/`readReceipts: true` to a session. If asked to "mark as read on WhatsApp," confirm intent — it contradicts covert monitoring.

## LID→PN resolution returns DEVICE-suffixed jids — canonicalize before chat-keying
`signalRepository.lidMapping.getPNForLID(lid)` (and occasionally `key.remoteJidAlt`/`participantAlt`) returns a jid WITH a device suffix, e.g. `<pn>:0@s.whatsapp.net`. Every chat key / participant / call jid elsewhere uses the BARE `<pn>@s.whatsapp.net` form. If you store the suffixed form as a chat key, the resolved contact/call lands in a DUPLICATE thread instead of the existing conversation. Strip the `:device` part (`user.split(":")[0] + "@" + domain`) on EVERY value out of getPNForLID/remoteJidAlt/participantAlt before caching or using it as a key. The clean `remoteJidAlt` path usually has no suffix (why earlier incoming threading worked), but getPNForLID (used for calls, which carry no alt) does.
**Why:** the `phone` display strips `:0` so it looks fixed while chat placement is silently wrong — easy to miss.

## Call events can REORDER — serialize per-call + guard terminal outcome
A single WhatsApp call emits multiple `call` events (offer/ringing → terminal timeout/reject/accept). Once `handleCall` is async (it must be, to await LID→PN), firing them with bare `void this.handleCall(c)` lets offer and terminal resolve CONCURRENTLY — a late offer can overwrite a terminal in-chat bubble back to "Incoming…". Two guards: (1) serialize via a `callQueue` promise chain (`this.callQueue = this.callQueue.then(() => handleCall(c))`) so the offer (and its LID cache fill) completes before the terminal; (2) keep a `callOutcomes` Map<callId,outcome> and never let a terminal (missed/rejected/accepted) be downgraded to a non-terminal. `saveCallLog` already preserves terminal in the DB via `onConflictDoUpdate CASE`, but the synthetic in-chat message needs its OWN guard.

## Calls render inline in the chat as a synthetic message (mediaKind="call")
Decision: besides the Calls page, each call is mirrored INTO the contact's conversation (WhatsApp-style) by `upsertMsg(counterpartJid, {id:`call:${callId}`, mediaKind:"call", fromMe:outgoing, text:"📞 <label>"})`, skipped for groups. Keyed by `call:<callId>` so offer→terminal updates ONE bubble (no media-download path touches it since it's created outside the upsert handler). Frontend `chats.tsx` special-cases `mediaKind==="call"` → PhoneMissed (missed/declined, red) / PhoneOutgoing (fromMe) / PhoneIncoming icon + the label (📞 stripped). Status participant LID→PN is resolved the same way (drives Status grouping + phone display); first status from an uncached poster may briefly show the LID until the mapping resolves — acceptable.

## Mobile browsers SUSPEND a backgrounded tab's EventSource + timers
"Live updates need a manual refresh" on mobile is usually NOT a broken SSE/persist path — it's that the mobile browser suspends the backgrounded panel tab's EventSource and intervals while the user is in the WhatsApp app, so on return the open chat looks stale until the next slow poll. Fix in `chats.tsx`: a `visibilitychange` + window `focus` effect that re-fetches chats/status and bumps the live-tick the instant the tab becomes visible again. SSE + the persist→SSE pipeline themselves were proven working via a self-send self-test (instant `event: message`).
**Why:** the user constantly switches WhatsApp↔panel; this exact workflow triggers the suspension.

## Per-message action menu (long-press / right-click) — scope + Forward limitation
The chat bubble menu (chats.tsx Conversation) opens on touch long-press (450ms timer, cancelled by tap/scroll via touchmove) OR `onContextMenu` (desktop right-click); call-type messages are excluded. Actions: Reply, Copy (text only, skips placeholder-emoji rows), Download (any `hasMedia`), Delete-for-everyone (own non-deleted only). Reply sets a reply bar above the composer and on send passes `quotedId/quotedFromMe/quotedText` to `POST /panel/send` → `multiWA.sendMessage(...quoted)` (engine already supported a minimal `{conversation}` quote — preview-level only, no media thumbnail). Outside-click overlay `fixed inset-0 z-40`, menu `z-50`.
**Forward is deliberately NOT implemented:** the engine has no forward helper and retains no raw protos, so a true media forward needs heavy backend work. Download covers save-and-share. Offer Forward as a separate follow-up if asked.
**Delete-for-everyone needs `?fromMe=` on the DELETE call:** the backend derives `fromMe` only from `req.query.fromMe === "true"`; omitting it builds a wrong Baileys delete key (fromMe=false + participant) and the revoke fails. The menu only exposes Delete for own messages, so pass `?fromMe=${msg.fromMe}`.

## "Show ALL chats" (#1) and "own posted status" (#7) are bounded by linked-device sync
`getChatList()` only returns `chatStore` entries, which are created on message upsert — chats with NO synced messages never appear, and `messaging-history.set` applies name/unread only to already-existing entries. `syncFullHistory:false` limits the initial dump. So "all my chats like WhatsApp Web" can't be fully solved client-side: it needs creating placeholder entries from `h.chats` (and these don't survive a PM2 restart unless persisted, since hydrate rebuilds from DB rows that only exist for chats-with-messages). Own-status (#7) capture depends on WhatsApp pushing your own `status@broadcast` to the linked device, which it often doesn't replay on history sync. Treat both as best-effort / partly WhatsApp-side, not pure code bugs.

## Call DURATION is fundamentally unavailable on a Baileys linked device — do NOT re-chase
Baileys `WACallEvent` (v7.0.0-rc13) has NO duration field — only `chatId, from, callerPn, isGroup, groupJid, id, date, isVideo, status, offline, latencyMs`. The ONLY way to derive talk time is timing the linked device's own `accept`→`terminate` events, which for phone-answered incoming calls (answered on the primary phone, not here) and phone-placed outgoing calls NEVER arrive. So duration shows only in the rare case both lifecycle events reach this device. The user's phone shows "Voice call 1 min" because that's the PRIMARY device's native telephony record — it is not synced to linked devices.
**Why:** user repeatedly asks for call duration (calls it the most important feature); it is a genuine WhatsApp/Baileys platform limit, not a fixable bug.
**How to apply:** keep the honest Roman-Urdu banner on the Calls page; record outcome/time/video-vs-voice/`callerPn`; show duration only when actually computed. Do NOT fabricate duration or attempt to extract it from messages/history — there is no dependable source. `callerPn` (now on the event) can improve contact resolution, not duration.

## Presence is keyed by the contact's PN jid — store/emit DUAL-key (PN + raw @lid)
The panel looks up presence by the chat's phone-number jid (`@s.whatsapp.net`). WhatsApp may address `presence.update` by either the PN or the privacy LID (`@lid`). Map `pnJid = lidToPn.get(id) ?? canonicalJid(id)` and store+`notifyPresence` under BOTH `pnJid` and the raw canonical id when they differ, so the PN-keyed UI finds it regardless of how WA addressed it. Still best-effort: if no LID→PN mapping exists yet, an @lid-only event can't synthesize the PN key, and last-seen/online depend on the contact's privacy + WA throttling. Stays subscribe-only (never `sendPresenceUpdate`).
**How to apply:** treat "presence not showing" as best-effort/empirical, not a guaranteed bug — the dual-key store is the cheap robustness fix; beyond that it's a WhatsApp privacy/throttle limit.

## Panel nav tabs must be ONE shared component on every view
The 4-tab bar (Chats|Groups|Status|Calls) must render on all panel views via a shared `PanelTabs` component, NOT inline in `chats.tsx` only. Chats/Groups are a LOCAL sub-tab on route "/" (`tab` state); Status/Calls are their own wouter routes. Navigating to Status/Calls otherwise drops the tab bar and strands the user (browser-back only). Carry the home sub-tab across routes via `sessionStorage["panelTab"]`: `PanelTabs` writes it; `chats.tsx` lazy-inits `tab` from it; from Status/Calls the Chats/Groups buttons set it then `navigate("/")`.
**Why:** user reported tabs disappear after opening Status/Calls.

## View-once media capture is inherently one-shot/flaky on a linked device
A view-once item has only ONE downloadable copy; first-attempt decryption can fail while keys settle. `downloadMediaWithRetry` (4 attempts, tight 400ms*n backoff) helps ONLY with key-settling, not with media already consumed/expired. Expect intermittent misses ("worked yesterday, not today") — it is not a regression. Frontend labels a media message "{text} · not available" only once it's >60s old AND still has no bytes, so genuinely-slow fresh downloads still render when they arrive. Turn on `WA_DEBUG_PROTO=1` to log per-download failure reasons on the VPS.

## In-memory chatStore must NEVER hold base64 media — it balloons RSS on the swapless VPS
The engine's in-memory `chatStore.msgs` is for dedup/lastMsg/ticks/unread/persist-notify ONLY; nothing reads its `media` for display (panel AND admin serve bytes lazily from DB via `getMediaById` → `/media/:id`, using `hasMedia` flags). Two leaks caused a ~1GB RSS on the 3.8GB **zero-swap** VPS (→ sluggish send/receive/refresh): (a) `hydrate()` used `.select()` (ALL cols incl `media`), pulling the whole media history (was 1.3GB / 381 rows) into RAM on startup; (b) `upsertMsg` retained the downloaded base64 in `entry.msgs`. Fix: hydrate selects an EXPLICIT metadata column list excluding `media`; `upsertMsg` nulls `stored.media` AFTER `notifyPersist` (DB write reads `m.media` synchronously into the Drizzle expr before the await, so clearing after is safe; re-persist on a re-seen msg is idempotent via COALESCE onConflict). Verified live: RSS 995MB→146MB, free 335MB→1521MB.
**Why:** swapless box + base64 media in DB = any in-RAM copy of media is pure bloat and an OOM risk.
**How to apply:** never `SELECT *` from `wa_messages` into the engine; keep base64 strictly DB-resident + lazy-served. If RSS climbs again, look for a new path retaining `media` in memory.
**Pre-existing gap (architect-flagged, NOT yet fixed):** if a delete-for-everyone lands after the media placeholder but before the async download finishes, the `!existing.deleted` guard in `upsertMsg` blocks the media backfill, so that deleted item's bytes may never persist — weakens anti-delete capture. Fix would allow media-only backfill on deleted rows while still blocking text overwrite.

## Call log = ONE in-place bubble, NEVER a separate "call end"
A linked/companion device receives `accept`+`terminate` TOGETHER at the moment the phone picks up, and never a genuine end event — so any separate "call end" bubble is a lie shown while the call is still ongoing on the phone. Render exactly ONE bubble per callId (`call:${callId}`), updated in place from the best-known outcome (callOutcomes, after the downgrade guard): missed→"Missed", rejected→"declined", accepted→"answered" (+duration ONLY when a real terminate-after-accept yields durationSec≥1 — basically never on a linked device), else neutral "call". Pin the bubble ts to call START (callFirstTs map) so later accept/terminate don't reorder it to the bottom.
**Why:** recurring user complaint that calls showed a premature/fake "end" mid-call.

## Media downloads need a live-vs-history PRIORITY lane, not just a flat cap
The flat semaphore (cap 3) alone still let a history-sync burst of old media occupy every slot and starve a LIVE view-once (one-shot, unrecoverable). Two lanes share the cap: LIVE waiters always served first; HISTORY capped at 1 concurrent (HISTORY_MAX). History-sync downloads go through the low-priority lane with fewer retries; live stays default/full retries. UI shows "downloading…" for fresh missing media and "couldn't load (one-time or expired)" only once stale (>60s).
**Why:** a view-once has ONE copy — a bulk backfill must never congest the single socket at the moment a live one-shot lands.

## Presence is effectively UNAVAILABLE in covert mode — not a bug
With markOnlineOnConnect:false + never sendPresenceUpdate (covert), WhatsApp delivers ~zero presence.update events, so online/offline/last-seen almost never appear. Hard platform tradeoff: to SEE others' presence you must broadcast your own, which breaks covert. Don't chase it as a code bug. UI shows real presence when an event does arrive, else "status unavailable" — never a fabricated "offline". Surface the tradeoff to the user honestly.

## Number-switch isolation: in-memory reset is a PARTIAL mitigation only
On connection "open", if a DIFFERENT number linked than last time, clear the transient in-memory caches (chatStore, presence, savedNames, groupNamesFetched, call maps, lidToPn). Track the previous number in a dedicated `lastLinkedPhone` field, NOT state.phoneNumber — the latter is nulled on disconnect, so a switch across a reconnect would go undetected. This does NOT fix the DB-level leak (see the "Per-account view" limitation): true isolation still needs the composite `(account_phone, jid)` schema migration. Never present number-isolation as fully fixed without it.

## Panel login username is CASE-SENSITIVE
The single panel user is `shoib` (lowercase), approved=true. Logging in as `Shoib` (capital S) 401s because the username lookup is exact-match (case-sensitive). Recurring "login broken / wrong password" reports are usually the capital-letter typo, not a real auth failure. (panel_user also stores password_plain so the admin can read it — accepted for a self-hosted single-user tool.)

## Incoming view-once is UNRECOVERABLE on a covert/linked device (only a placeholder is possible)
The earlier "download the UNWRAPPED message" note only works WHEN the view-once actually decrypts. In practice, incoming view-once on a covert companion device usually arrives with NO decryptable content at all — the messages.upsert fires with `msg.message == null` (logged as `hasMsg:false, topKey:null, stub:null` under WA_DEBUG_PROTO=1) while normal text in the SAME chat decrypts fine. WhatsApp deliberately withholds the openable view-once payload from companion/linked devices — the exact reason official WhatsApp Web shows "you can only open this on your phone". Baileys' silentLogger hides the underlying decryption error. The media bytes are therefore NOT capturable from this device, full stop.
**What we do instead:** in the live `messages.upsert` handler, when `!msg.message` (live notify, not fromMe, not status), upsert a plain-TEXT placeholder bubble ("🔒 View-once or protected message — can only be opened on the phone") keyed on `msg.key.id` so the arrival + its time are at least visible. Plain text (no mediaKind) means it renders even on a stale/cached frontend. Dedup by id means retries of the same failed message don't inflate unread.
**How to apply:** treat "view-once media not showing" as a PLATFORM LIMIT (same class as presence and answered-call duration), not a fixable download bug. Don't promise recovering the actual photo/video from a linked device.
